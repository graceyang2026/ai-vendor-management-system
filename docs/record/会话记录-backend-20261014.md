## 17:12 · Refactor 补记：清理调试残留时揪出一处真实单测缺陷，并撤销 17:01 的错误归因

> 摘要：收尾自检发现 `SupplierServiceImplTest:503` 残留调试期写下的 `withFailMessage("DIAG …")`，还原成常规断言后 `./mvnw clean test` **真实失败**；查根因后确认是我补的单元测试本身有缺陷（不是环境问题），修正后 218 用例全绿、门禁再次 PASSED。**本节同时作废 17:01 小节"过程注记"里"增量编译行号错位所致假失败"的判断——那个判断是错的。**

- **接到任务**：本轮无新派发，属上一节任务的收尾自检（清理残留 + 复跑门禁 + 出完成报告）。
- **真实根因（实测，非推测）**：MyBatis-Plus 3.5.7 的 `LambdaQueryWrapper` 是**在生成 SQL 段时才把绑定值写入 `paramNameValuePairs`**。原用例先 `wrapper.getParamNameValuePairs()` 再断言，此时 map 为空 → `containsValue("NORMAL")` 恒 false。
  - 取证一（同一次运行内打印）：`DIAG2 class=java.util.HashMap map={} contains=false vals=[]` —— 未触发 `getSqlSegment()` 时参数表确实是空 HashMap。
  - 取证二（上一轮插桩时 `wrapper.getSqlSegment()` 与 pairs 同时打印）：`{MPGENVAL1=DRAFT, MPGENVAL2=RETURNED, MPGENVAL3=2, MPGENVAL4=NORMAL, MPGENVAL5=%杭州%, MPGENVAL6=%杭州%}`，SQL 段为 `((status NOT IN (…) OR created_by = …) AND status = … AND (name LIKE … OR tax_no LIKE …)) ORDER BY created_at DESC` —— 实现侧下推完全正确。
