## 3. 详细规格

### 3.1 UserResponse（沿用 api-spec §6，全字段显式 snake_case）
```json
{ "id": 2, "username": "staff01", "real_name": "张三", "role": "STAFF", "enabled": true, "created_at": "2026-10-08T11:08:30" }
```
> `password_hash` 绝不出现在任何响应（模块 1 既有铁律）。

### 3.2 POST /users — UserCreateRequest
```json
{ "username": "newstaff", "password": "New@12345", "real_name": "李四", "role": "STAFF" }
```
校验规则（违反 → 40001 + 具体提示）：
- username：必填，3-50 字符，`^[a-zA-Z0-9_]+$`；**唯一性冲突 → 40903**（见 §4）
- password：必填，≥8 位且同时含大写、小写、数字（与演示账号 Admin@123 风格一致）；BCrypt 入库
- real_name：必填，≤50
- role：必填，ADMIN/STAFF/AUDITOR 枚举

成功：HTTP 200 `ApiResponse.success(UserResponse)`；审计 `entity_type=USER, action=CREATE_USER, old_status=null, new_status="true", comment="创建用户 {username}，角色 {role}"`

### 3.3 PATCH /users/{id}/status — `{ "enabled": false }`
- 目标不存在（或已逻辑删除）→ **40401 用户不存在**
- **本人限制**：ADMIN 不能停用**自己** → **40302** `"不能停用当前登录账号"`（防自锁，铁律）
- enabled 变更需幂等：目标状态与当前一致 → 直接成功返回（不重复写审计）
- 审计：`action=ENABLE_USER/DISABLE_USER, old_status="true/false", new_status="true/false", comment="停用用户 staff01"`
- 停用的即时效果：CustomUserDetailsService 已对 `enabled=false` 拒登（模块 1 已实现，无需新代码）；**已签发 JWT 在有效期内仍可用**——MVP 接受（见 Q3）

### 3.4 PUT /users/{id} — UserUpdateRequest（本稿新增）
```json
{ "real_name": "李四", "role": "AUDITOR" }
```
- 仅允许改 `real_name`、`role` 两字段（username、password 不可改——改密码属 Q1）
- 目标不存在 → 40401；role 非法枚举 → 40001
- **本人限制**：ADMIN 不能修改**自己的角色** → 40302 `"不能修改当前登录账号的角色"`（防权限混乱/自锁）
- 审计：`action=UPDATE_USER, old_status=null, new_status=null, comment="资料修改: real_name 李四→李四四; 角色调整: STAFF→AUDITOR"`（old/new status 列不改状态故留空，变更内容放 comment）
- 角色调整即时生效说明：JWT 里的 role 是签发时快照，**改角色后需重新登录生效**——写入响应 message 提示前端（见 Q3）

## 4. 契约错误码增补（提请修订契约文档 3.2 节）

| code | 名称 | 场景 | 是否新增 |
|---|---|---|---|
| 40001 | VALIDATION_FAILED | 字段格式/枚举非法 | 复用 |
| 40302 | STATUS_NOT_ALLOWED | 停用/修改自己 | 复用 |
| 40401 | NOT_FOUND | 用户 id 不存在 | 复用 |
| **40903** | **USERNAME_DUPLICATE** | 用户名已存在（含被逻辑删除占用） | **新增**（40902 已于裁决 20261010 放宽为通用“业务冲突”族（在途申请 / 同周期在途评价单 / 税号唯一性）；用户名冲突需独立提示语与定位（含被软删永久霸占键位的特殊语义），故另立 40903 而不复用 40902；message：“用户名已存在”） |

## 5. 契约审计增补（提请修订契约文档 4.1/4.2 节）

- `EntityType` 增加 **`USER`**（现 4 值 → 5 值）
- `action` 枚举增加 **`CREATE_USER` / `UPDATE_USER` / `ENABLE_USER` / `DISABLE_USER`**（现 7 值 → 11 值；api-spec §6 审计行已预先定义这 4 个名）
- 约定：用户管理审计 `entity_id` = 目标用户 id；`old_status`/`new_status` 记录 enabled 字符串 `"true"/"false"`（CREATE_USER 时 old 为空；UPDATE_USER 均空、变更写 comment）
- 实现方式：模块 4 的 `AuditLogService.record(...)` 零改动，仅扩两枚举

## 6. 数据库对齐

- **复用现有 `sys_user` 表，零 DDL**：uk_username 唯一键、enabled、deleted 逻辑删除列均已就绪（线上核实一致）
- 已知边界（记忆库坑点）：`uk_username` 不含 deleted → 逻辑删除后的 username 永久占用，40903 的 message 应区分"已存在"而非提示可重试
- 实体 `User.java` 现未映射 `deleted` 字段：列表/查询暂不过滤逻辑删除（MVP 无删除功能，无实际影响；若 Q2 通过则需补 @TableLogic）

## 7. 安全与角色铁律

- 全部端点 ADMIN 专属：角色不匹配 → Security 层 403+40301（模块 2 机制，零新代码）
- ADMIN 不参与供应商业务的边界不变（TDD L108 管理权/业务权分离）
- Service 层二次校验（防 Controller 漏注解）：写操作调用 `roleGuard.requireRole(Role.ADMIN)` + 本人限制用 `requireSelf` 的反向语义（新增 `requireNotSelf(Long id)` 或业务判断，实现期定）
- 审计写入遵循模块 4 隔离铁律：record 失败不影响用户管理主事务
