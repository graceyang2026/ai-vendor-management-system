# 会话记录：审计日志新增"用户管理"动作（entity_type=USER）

- 日期：2026-10-08
- 分支：MVP-W3
- 主题：从"查看数据库表"出发，讨论审计日志 action/status 语义，最终决定为管理员用户管理补齐审计契约，并同步代码与文档。

---

## 一、会话脉络（Q&A）

1. **查看数据库表**：`vendor_db` 共 7 张表（sys_user / supplier / supplier_qualification / performance_evaluation / performance_evaluation_draft / lifecycle_request / audit_log）。仅 `sys_user` 有 3 条演示账号，其余为空。表结构事实源为 `srm-backend/src/main/resources/schema.sql`。
2. **audit_log 字段**：确认 11 字段（id, entity_type, entity_id, operator_id, operator_role, action, old_status, new_status, result, comment, created_at），append-only，无 updated_at / deleted；索引 (entity_type,entity_id)、operator_id、created_at。
3. **new_status/old_status 与 action 是否相同**：不是。action=动词（做了什么），old→new_status=业务单据状态迁移的两端；result=操作本身成败，与 new_status 也不同。示例：action=AUDIT_APPROVE、old_status=PENDING_AUDIT、new_status=APPROVED、result=SUCCESS。
4. **action 有哪些**：审批流 7 个 SUBMIT / AUDIT_APPROVE / AUDIT_REJECT / REVIEW_APPROVE / REVIEW_REJECT / DECISION_APPROVE / DECISION_REJECT。无用户管理动作。
5. **管理员新增用户是否要审计**：当时结论——`/users` 接口尚未实现（无 UserController/Service），且 `record()` 全项目无调用点。
6. **需求文档（TDD.docx）核对**：TDD 是概念级，ADMIN 职责含"创建、启用、停用内部用户账号"；审计原则句为"关键操作必须记录操作者、时间、操作类型、旧状态、新状态、结果"，但未点名用户管理留痕；下游契约（api-spec §5、数据库设计 §8）的 entity_type 未含 USER。存在模糊口子。
7. **决策**：采用"从严"方案——补齐用户管理审计契约，动作集为 `CREATE_USER / UPDATE_USER / ENABLE_USER / DISABLE_USER`，EntityType 增加 `USER`。

---

## 二、关键决策与依据

- **DDL 无需改**：schema.sql 的 `action`/`entity_type` 均为 `VARCHAR(50)`，无 CHECK、不用 MySQL ENUM（见数据库设计 §11.4），取值合法性由应用层枚举约束，扩展枚举不需 DB 迁移。
- **必须同步枚举事实源**：代码注释与 api-spec 都写"完整枚举见数据库设计文档第 8 节"，故《SRM 后端数据库表设计.md》§8 是 action/entity_type 权威定义，必须与代码对齐。
- **TDD.docx 不改**：概念级原则已覆盖，不含枚举清单；矩阵澄清属可选。
- **顺带修正文档 bug**：数据库设计 §8 result 原写 `SUCCESS/FAILED`，与代码 `AuditResult`（SUCCESS/REJECTED）及 api-spec 不符，改为 `SUCCESS/REJECTED`。
