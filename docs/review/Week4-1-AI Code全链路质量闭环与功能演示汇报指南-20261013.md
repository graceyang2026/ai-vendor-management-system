## 第一部分 业务背景（先讲为什么，不讲技术）

供应商管理当前完全依赖线下与人工维护，六项结构性痛点（源：《供应商管理系统需求规格说明书》V1.6_20261011 §1.1，docx 只读解析）：

1. 供应商基础信息分散，数据一致性难以保证；
2. 历史供应商档案检索效率低；
3. 准入审批缺少统一线上流程；
4. 资质文件管理不集中，历史资料追溯困难；
5. 状态变更与绩效评价缺少统一管控；
6. **业务操作及审批过程缺少完整系统留痕**——这是合规审计的硬伤。

> 汇报建议：此处用 1 分钟讲清"痛点 6 是本项目立项的第一驱动力"，因为它直接决定了架构上"审计留痕"是一等公民而非附属功能。真实业务量化数据（供应商总数、线下审批平均耗时、资质遗失案例）**待项目负责人补充**。

## 第二部分 方案价值

| 价值主张 | 落地机制 | 对应验收条款 |
|---|---|---|
| 权责分离，杜绝"既当运动员又当裁判" | RBAC 三角色：ADMIN 零业务写、STAFF 只提事实与申请、AUDITOR 只做决策不改状态 | acceptance §4.2 / §4.3 |
| 供应商全生命周期可视、可控、不可跳步 | 六态状态机 + `LifecycleRequest` 两步申请（停用/恢复/淘汰） | acceptance §1.1 / §1.3 |
| **绩效打分不可人为操纵** | 前端物理上无分数入口，算分由后端硬编码引擎完成 | acceptance §2.1 / §2.3 |
| 无业务期间不被误杀 | 零业务免考机制（Q/D 双维度对称） | api-spec §4.1 |
| 任何关键动作可追溯到人、时间、原/新状态、结果 | 全量 `AuditLog` + 行级隔离（规则 C） | acceptance §3.1 / §4.4 |

## 第三部分 架构风险取舍（Trade-offs）—— 技术总监视角

> 这一节是 Review 的得分点。评审组要看的不是"我们做了什么"，而是"我们在岔路口为什么选这条路、代价是什么"。

| # | 取舍点 | 选定方案 | 被拒方案与理由 | 代价 |
|---|---|---|---|---|
| T1 | 绩效打分入口 | 前端只提交**客观事实**（8 个事实字段），后端算分 | 拒绝"线上 Excel 式手工打分"（V1.5 修订明确取消纯手工打分）；拒绝前端传分 | 演示时无法"手工调分"，业务方需理解事实→分数的映射 |
| T2 | 无业务期间算分 | `qc_total_batches=0` → Q=100，**对称扩展** `total_batches=0` → D=100 | 拒绝按 0 分处理（会造成无业务期供应商被误评 D 级淘汰）；拒绝抛除零异常 | `quality_exempt` 列名与"整体免考"语义不完全贴合，已作为历史命名债登记 |
| T3 | 免考标识建模 | MVP 复用**单一** `quality_exempt`，不拆 `delivery_exempt` | 拒绝加列（MVP 极简，减少 DDL 与 DTO 面积） | 未来若需分维度免考统计，需一次 DDL + 契约变更 |
| T4 | 资质审核留痕编码 | **方案甲：零新增码值**，复用 `REVIEW_APPROVE/REJECT`，靠 `entity_type=SUPPLIER_QUALIFICATION` 区分域 | 拒绝新造 `REVIEW_QUALIFICATION`（会造成前后端字典双份维护） | 一码多域，前端展示文案必须按 `entity_type` 分流（已实现并有测试锁定） |
| T5 | "同供应商同证照仅一条现行版"约束 | 生成列 + **部分唯一索引**（`approved_key`/`tax_no_active`/`active_period_key`/`active_key`） | 拒绝触发器（不可移植、难测试）；拒绝应用层裸查（并发漏网） | 生成列表达式需团队理解，已沉淀为可照抄范式 |
| T6 | 算分引擎形态 | `PerformanceScoreCalculator` 为**纯函数**，布尔入参 `hasExpiredApprovedQualification` 由 Service 预先查好传入 | 拒绝在计算器内注入 Mapper（会把纯函数变成不可测的组件） | 查库职责落在 Service，多一次编排代码，但换来 100% 分支可测 |
| T7 | 审核员日志可见范围 | 展示范围裁剪由**前端显式传 `entity_type` 列表 + 后端按参数过滤**实现；规则 C 之下 AUDITOR 本就全量可见 | 拒绝把它包装成"新安全边界"（会误导团队以为安全靠传参） | 安全边界与展示范围必须分开叙述，汇报时不能说"AUDITOR 看不到 USER 日志"，只能说"日志页不展示" |
| T8 | 数据权限模型 | 仅"本人 + 状态"两维（规则 A/B/C），复用 `RoleGuard` 三方法 | 拒绝引入部门树 / 数据权限组等多维模型（MVP 过度设计） | 未来跨部门协同需重构可见性层，已显式声明范围 |
| T9 | 逻辑删除 vs 物理删除 | 全量逻辑删除（`deleted` 位），正式档案禁止物理删除 | 拒绝物理删除（会造成审计追溯断档） | 查询需恒带 `deleted=0`；历史数据只增不减 |
| **T10** | **乐观锁落地状态（诚实风险）** | 契约要求 `Supplier`/`PerformanceEvaluation` 带 `version` 并由 MyBatis-Plus 校验 → `40901` | 拒绝"前端传版本号但后端不校验"的伪实现 | **当前全库无任何实体标注 `@Version`（实测：仅 `MybatisPlusConfig` 注册了拦截器）**。并发防线在代码层尚为真空，必须随卡 A/D 落地，否则 `40901` 是永不触发的死码 |

## 第五部分 Task 1 全链路图景：供应商基础建档与税号唯一性校验

### 5.1 上下游依赖（目标态架构，据契约绘制）

```
[登录 JWT]──►[前端 SupplierListView / 建档表单]
                    │  POST /api/v1/suppliers  (snake_case, Bearer token)
                    ▼
        [JwtAuthenticationFilter] ──► [Controller @PreAuthorize('STAFF')]   ← 角色粗粒度
                    │
                    ▼
        [Bean Validation: @NotBlank/@Pattern]  ──失败──► 40001（HTTP 200 + body.code）
                    │  通过
                    ▼
        [SupplierService.create]  ── 应用层税号预检 ──撞在途──► 40902
                    │  初始 status=DRAFT, created_by=当前用户, version=1
                    ▼
        [DB: supplier 表]  唯一索引 + 生成列 tax_no_active（逻辑删除后置 NULL，释放税号）
                    │
                    ▼
        [AuditLogService.record]  entity_type=SUPPLIER, action=CREATE/…（try-catch 防崩溃，绝不阻断主事务）
                    │
                    ▼
        下游：submit（需未过期营业执照）► PENDING_REVIEW ► audit（同事务连带批复资质）► NORMAL
        可见性：规则 A（本人 DRAFT/RETURNED）+ 规则 B（准入后公有只读）
```

## 第六部分 Task 2 全链路图景：绩效评价自动化算分引擎

### 6.1 数据流（严格体现防篡改铁律）

```
[STAFF 发起单次评价] POST /performance/evaluations  { supplier_id, period_start, period_end, mode, fact_record? }
        │
        ├─ mode=manual ─► [ManualFactInputAdapter] 校验：非负 / qc_failed≤qc_total / delayed≤total / 上限域  ─失败─► 40001
        └─ mode=mock   ─► [MockDataMetricAdapter] 确定性种子生成，**前端传入的 fact_record 被忽略而非报错**
        │
        ▼  Controller 按 mode 从 Map<String, PerformanceMetricProvider> 取 bean（禁止 if/else 判模式）
[在途单去重] 同 supplier+period 存在 PENDING_REVIEW/RETURNED ─► 40902；DB 唯一索引 uk_supplier_active_period 兜底并发
        │
        ▼
[查资质过期] Service 预检 → hasExpiredApprovedQualification: boolean
        │
        ▼
[PerformanceScoreCalculator.calculate(fact, hasExpiredApprovedQualification)]  ← 纯函数，无 DB 依赖
   Q = MAX(0, 100 - qc_failed/qc_total*100*1.5 - major_accidents*50)   qc_total=0 → Q=100 且免考
   D = MAX(0, 100 - delayed/total*100 - avg_delay_days*2)              total=0   → D=100 复用同一免考标识
   综合 = Q*30% + D*25% + P*20% + S*15% + C*10%
   评级 A≥90 / 80≤B<90 / 70≤C<80 / D<70 ；C=0 当且仅当存在已过期通过资质
   risk_warning = 资质过期 || grade∈{C,D}（**绝不自动变更供应商状态**）
        │
        ▼
[落库 performance_evaluation（24 列，DECIMAL(5,2)）] status=PENDING_REVIEW
        ▼
[AuditLog: action=SUBMIT, entity_type=PERFORMANCE_EVALUATION]（一步式发起复用 SUBMIT，靠 entity_type 区分域）
        ▼
[AUDITOR 复核] REVIEW_APPROVE→APPROVED 归档终态 / REVIEW_REJECT→RETURNED（沿用同一条记录不新建，重提回 PENDING_REVIEW）
        ▼
[前端只读回显 16 字段 Response（含 mode）]  ← 无任何分数写入通道
```

### 6.2 演示话术（评审组最可能追问的三点）

1. **"能不能从前端改分？"** —— 不能。`PerformanceFactRecord` 物理上不存在分数/评级/免考字段（契约 §4 + 实存 `PerformanceFactRecord` 设计），且 `GlobalExceptionHandler` 不接受业务侧分数入参。
2. **"没有业务的季度会不会被误评 D 级？"** —— 不会，双免考机制直接给 100 分并打 `quality_exempt` 标签。
3. **"评了 D 会不会自动停用供应商？"** —— 不会。停用必须 STAFF 提 `SUSPEND` 申请、AUDITOR 裁决（acceptance §2.4 + api-spec §3）。
